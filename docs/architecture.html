Software Factory · 架构图

多智能体软件工厂,基于 pi-mono 的 @mariozechner/pi-agent-core。 由 GitHub Issue 驱动,通过六个独立 Agent (每个拥有自己的 SKILL.md) 穿越完整的软件研发流水线,产出可合并的 PR。 用户面 CLI 已统一为 factory(bin/factory.js),工厂以预打包的 dist/ 形式随 npm 发布。
SCOPE   full pipeline + control panel
RUN MODES   cloud · local daemon · cli · panel
EXEC MODE   llm (production, only mode)
蓝色实线 · 数据流 Issue payload、API 请求、Agent→Tool 调用、Control Panel 读盘。
琥珀色虚线 · 控制流 Agent 编排、状态转移、commit/push、merge 决策。
紫色点线 · LLM 推理 送往 Anthropic 兼容 API 的 tool-calls,以及 Improve-Review-PR 的外环自反馈。
绿色 · 通过 / 终态 APPROVE、verified、merged PR 等表示成功的灯泡。
主要简化与假设　· 　将六 Agent 平铺为 conveyor,而实现里 Review-PR 与 Verify-Behavior 串接在 Implementation 之后、Improve-Review-PR 是独立的日级外环(紫色虚线表示这一回流路径)。 　· 　生产能力均通过 pi-agent-core 的模型与工具循环执行;测试用 echo adapter (FACTORY_MODEL_ADAPTER=echo) 替换真实模型以避免烧额度。 　· 　外部三块(GitHub Repo / LLM Provider / 本地 .factory/ state)在原代码里以函数 / 文件 API 形式分散;此图把它们归集到右侧"EXTERNAL"列,以表达它们的来源不同(GitHub 网络、LLM HTTP、磁盘)。 　· 　用户面 CLI 已统一为 bin/factory.js(子命令 install · start · panel · uninstall),它内部 spawn factory-daemon.mjs 与 bin/factory-panel.js 作为子进程,故入口层把这三者画成一张统一的"factory CLI"卡片。 　· 　构建产物(dist/factory/orchestrator.js + dist/factory/skills/*.json + dist/panel/)通过 build-factory.mjs(esbuild)与 build-panel.mjs(vite)产出,在 npm tarball 里随包发布;SkillLoader 运行时只读 dist/factory/skills/*.json。 　· 　factory/ 子目录是安装器把 runner 自身源码复制进目标 workdir 的结果,通过 git diff ... -- :!factory 路径过滤从审查 diff 中排除,避免误触发审查规则。
