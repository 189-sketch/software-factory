# Harness² 对 Software Factory 的启示

研究日期：2026-10-19。
本项目基于当前工作树分析，HEAD 为 `1d1f3548146b789702d879a5448e81fbf83fd478`，包含尚未提交的修改，不能将本报告的实现判断等同于该提交的历史状态。
外部项目固定为 [google-research/harness2@1cfe254](https://github.com/google-research/harness2/tree/1cfe254e8d25b15f37048c3730134686abe60335)。
本文只提出分析和验证方案，没有修改产品代码，也没有执行真实模型实验或 GitHub 写操作。

## 1. 判断

最值得借鉴的是：把 harness 的改进当作一项需要执行证据和对照试验的工程活动。
对本项目而言，下一步应当是让已有的评审经验改进循环具备可验证性，再考虑扩大自动优化的范围。

本项目已经解决了不少生产执行问题，包括阶段输入、代码版本绑定、独立判断、验收收据、外部操作恢复和人工审阅 skill 变更。
Harness² 提供的是围绕这些执行能力的优化方法，适合成为受约束的实验层，不能替代现有状态机和交付门禁。

本报告将官方论述、源码实现和针对本项目的建议分别表述。
论文的 benchmark 提升不能直接推算为本项目的软件交付成功率提升。

## 2. Harness² 的核心方法

[官方论文](https://arxiv.org/abs/2610.14224)描述了固定模型权重、改进模型外围执行系统的两层递归。

第一层针对当前任务执行 Propose → Probe → Compose。
先提出通用和领域相关的 harness 改动，再用同一任务实际执行，最后比较不同执行过程，组合出新的 harness。
可修改的范围包括系统提示、guardrails、memory、工具指导、子代理、skills、scripts 和 plugins。
这些能力的存在不代表它们都适合在生产工厂内自动开放。

第二层把采纳的 harness 和有执行证据支持的经验写入领域库，影响后续任务的改进过程。
[实验说明](https://github.com/google-research/harness2/blob/1cfe254e8d25b15f37048c3730134686abe60335/docs/EXPERIMENTS.md)要求同一领域按任务顺序运行，只读取更早的经验，并按实验配置隔离库。
这种实现属于经验库驱动的持续适应，不应理解为训练模型权重。

并行递归扩大候选探索范围，顺序递归在前一轮的基础上继续调整。
两种方式都会增加实际任务执行和改进模型调用，不能把递归预算当成免费的推理质量开关。

## 3. 与本项目的对应关系

| 方面 | Harness² 的做法 | 本项目当前依据 | 启示 |
| --- | --- | --- | --- |
| 改进对象 | 模型外部的多种 harness 组件 | `skills/`、系统提示、工具约束、运行时和独立判断已分层存在 | 先明确允许变化的指导层与必须固定的交付规则 |
| 当前任务优化 | 同任务提出候选、试跑、比较、组合 | 已有重试、定向修复和恢复机制 | 修复产品与改进执行方法需要分别记录，不能混为一次 retry |
| 跨任务学习 | 按领域保存经验和已采纳 harness | `improve-review-pr` 从人工反馈提出 review skill PR | 已有外层循环的起点，应优先补对照验证 |
| 输入追溯 | 保存实验命名空间、候选与执行产物 | StageInputManifest、必需规则哈希、会话输入身份 | 在已有输入证据上补齐完整 harness 快照 |
| 执行后端 | OpenCode、Codex 适配 | AgentRuntime 已有统一入口，当前注册集合仅为 `claude-code` | 保留适配边界，不因研究而重建运行时或立即引入多后端 |
| 质量判断 | 执行轨迹对比和候选选择，另行 benchmark grading | 规格评审、PR 评审、独立判断、行为验收和 commit 绑定 | 候选选择只指导优化，现有门禁继续决定能否交付 |
| 外部副作用 | 以 benchmark 运行与产物为中心 | 工厂会发布评论、创建分支/PR，并可能合并 | 候选试验必须隔离真实 GitHub 写入 |

本地实现主要参见 [improve-review-pr.ts](../src/agents/improve-review-pr.ts)、[agent-runtime.ts](../src/core/agent-runtime.ts)、[project-context.ts](../src/core/project-context.ts)、[completion-contract.mjs](../runtime/completion-contract.mjs) 和 [external-op-ledger.ts](../src/core/external-op-ledger.ts)。
历史 roadmap 和部分架构注释仍描述过往 SDK 或后端愿景，本报告以可执行源码为准。

## 4. 六项值得落地的启示

### 4.1 从记录经验走向验证经验

当前 `ImproveReviewPrAgent` 已经收集人工反馈、生成关联反馈 ID 的 learning，并通过 PR 提议更新 `.agents/skills/review-pr/SKILL.md`。
其系统提示明确要求人工审阅后才激活，证据不充分时可以不生成 learning。
这比没有来源约束的自动记忆更适合生产工厂，应当保留。

缺少的环节是：一条新规则是否减少了误报、漏报和评审往返，同时没有降低必要缺陷的检出率。
当前这条路径没有在发布建议 PR 前对旧版与候选版执行同任务对照。
因此，建议首先为 review skill 的改动附上固定样本上的基线与候选结果，而不是先扩展更多自改写组件。

每条候选经验至少应保留反馈来源、关联执行证据、适用阶段、适用仓库/技术栈、反例和验证结果。
人工反馈是一种学习信号，不能自动当作质量标签；标签需要结合规格、代码及复核结果建立。

### 4.2 优化执行策略，固定质量标准

Harness² 将 guardrails 也放进可编辑组件，但本项目的完成条件承担真实交付责任。
建议先允许调整检索顺序、上下文组织、工具使用指导和补充技能，固定验收条件、独立判断要求、权限边界及合并规则。

例如，候选可以建议 reviewer 先沿持久化调用链检查失败传播。
候选不能把“持久化失败后仍报告成功”降成不阻断问题，以制造更高的 APPROVE 比例。

本项目的 `hasImplementationApproval` 同时约束规格批准、评审 commit、验收 commit、语义判断和 AC 收据覆盖。
优化器不得通过修改这些条件证明自己有效。
这里的经验来自 Harness² 的可变 harness 思路，约束边界则是针对本项目的设计建议。

### 4.3 为每次运行固定完整 harness 身份

现有实现已经有规则正文哈希、构造后的提示、会话输入身份以及阶段产物引用。
但这些分散信息尚不能直接视作一个完整、不可变、可比较的 harness 版本。
特别是 `buildStageInputManifest` 当前返回的 `rules` 为 `[]`，虽然实际 dispatch 会另外加载和注入 requiredRules，但阶段记录自身没有填入这些规则引用。
这是引入实验前需要明确补齐的追溯环节。

建议完整记录角色提示与输出契约、实际读取的 skill/规则内容哈希、工具契约、模型/后端配置、工厂 build、输入产物及经验库版本。
记录的是实际生效内容，不能只记录包版本或默认路径。
该快照可用于对照、恢复和归因，不保证随机模型产生字节一致的输出。

新候选不应直接复用基线已经读取旧指导的 provider session。
可比较的试验需要相同任务背景和文件快照，以及各自独立的会话与工作目录。
否则会把候选改进与对话历史差异混在一起。

### 4.4 把行为差异变成可核验的证据

同一个任务由旧规则和候选规则分别执行，才有机会观察规则是否改变了行为。
但轨迹对比只是准实验，模型采样、网络、依赖状态和可见上下文都可能成为混杂因素。
有价值的信号需要通过重复样本和独立检查确认。

对于 review-pr，可以比较实际读取的文件、检索调用、证据定位、最终 finding、规格关联和独立判断结果。
示例：基线只引用 diff，候选读取固定版本的关联函数并正确指出被人工确认的故障传播问题。
这比“候选解释更完整”更能支持一条新指导。

同时必须保存负例：候选是否把原本不成立的风险写成阻断 finding，是否因过度检索耗尽预算，是否漏掉别类问题。
组合多条建议时仍需重新执行验证，不能假设各条局部有效的建议组合后必然有效。

### 4.5 经验按作用域读取，避免无条件追加

本项目的交接说明已经强调历史笔记不是验收证据，当前评审必须读取当前版本证据。
跨 Issue 经验也应保持这条边界。

建议先按仓库、阶段和技术栈组织经验，并注明生效版本与撤回条件。
例如，某个仓库的 UI 布局约定不能自动变成所有项目的阻断规则。
学习规则要经过验证才能从局部作用域推广。

先采用简单的文件/清单检索即可，不需要为了借鉴经验库立即引入向量数据库或新的存储服务。
对冲突、重复和失效规则应有显式替换机制，不能长期只向 SKILL.md 末尾追加。
更复杂的检索设施应由真实经验规模与检索失误证明其必要性。

### 4.6 将递归预算与故障恢复预算分开

基础设施失败不说明产品有缺陷，也不说明候选 harness 较差。
本项目已经区分运行故障、产品断言失败和证据不足，应延续这种分类进入实验结果。

建议分别记账：基础设施恢复、产品修改、harness 试验和最终独立验收。
同一任务中消耗更多轮次不等于有更多学习收益。
只有新的候选假设和可比较的新证据，才值得消耗优化预算。

成本应包括失败调用、基线试跑、候选试跑、组合执行、选择、反思和后续验证。
在相同模型条件下比较质量，再与相同总调用/令牌预算的简单重复执行进行比较，才能区分 harness 优化与额外采样带来的收益。

## 5. 不宜照搬的部分

### 5.1 最终采纳不保证优于基线

源码研究确认，最终候选池只包含组合后的 finals，不包含 base。
`k=1` 时走 trivial selection，仅检查产物可读，并不执行候选与基线的质量择优。
`k>1` 的选择器也只在 finals 内选择，不能退回 base。
具体源码位置与成本核算见[外部源码研究笔记](harness2-source-research-2026-10-19.md)。

本项目应允许 `keep_baseline`、`adopt_candidate` 和 `insufficient_evidence`。
选择器的模型判断不能单独授权经验推广，更不能授权产品合并。
没有达到预设改进条件时保留原方案，是生产优化层应具备的行为。

### 5.2 不把单步递归当成低成本重试

该版本正常路径每个任务需要 `4k` 次 solver rollout 和 `3k` 次 propose/compose 调用，另外有 reflection，`k>1` 还有选择器。
这里 solver rollout 是完整任务执行，不能等同于单次简单模型请求；内部工具循环和重试另计。
因此，`k=1` 也已经是一组昂贵的实验。

不建议默认对每个 Issue 的每个阶段进行递归探索。
应先在离线样本上证明收益，再对失败集中、收益足够高的阶段启用有限试验。

### 5.3 不把研究评测结果等同于生产交付收益

官方声称在 WorkBuddy-Bench、JobBench 和 LAB 上取得提升，但这是论文特定模型、harness 与评测设置下的结果。
它没有证明本项目的误合并率、维护者工作量或单位成本交付率会按同样比例改善。

官方实验说明还明确记录过 Codex 执行从网上取回公开 rubric 的情况，并提示执行器默认网络不受限、Codex sandbox 被关闭。
这说明评测答案隔离和执行隔离需要另外设计。
这里应借鉴其公开披露局限的做法，而不是复制默认权限配置。

对于本项目，Issue、仓库文件和人工反馈也是不可信输入，不能因为被写入经验库就取得改变权限或验收规则的权力。
实验的评估标签也必须从候选执行环境中隔离。

## 6. 建议的实施顺序及验收标准

### 第一步：先补可归因的运行记录

范围是串联现有规则哈希、会话输入、模型配置、build 和阶段产物，形成可保存的 harness 快照。
检查当前 StageInputManifest 的规则字段与实际 dispatch 内容是否一致，并显式标注缺失值。
通过标准：从任意一组实验记录可以恢复实际输入与指导，配置改变会改变实验身份，不允许混用旧结果。
这一步先设计记录契约和验证方式，不需要重构运行时。

### 第二步：只对 review-pr 做离线对照

复用当前 `improve-review-pr` 的候选建议来源，在发布建议 PR 前增加基线与候选试验报告。
选取约 20-30 个经过人工复核的历史 PR 作为探索性样本，覆盖真实缺陷、无缺陷和证据不足情形。
预留独立样本，候选生成不得读取其标签；这个规模只用于可行性判断，不足以证明普遍有效。

保持相同代码、规格、输入和模型配置，给基线与候选分别创建会话和只读工作环境。
评价缺陷检出、误报、证据准确性、判断分歧、重试次数、令牌使用和耗时。
通过标准：必要质量指标不退化，预先指定的主要指标有可解释改善，且改善超过重复执行的波动。
无法支持改善时产出保留基线的报告，不必为了实验结束而生成规则变更。

### 第三步：小范围启用并保持可撤回

经人工审阅的 skill PR 合并后，仅在约定仓库与角色作用域启用，并让新运行绑定新 harness 身份。
经验激活、回滚、撤回和替代都应可追溯，进行中的运行不应静默换规则。
通过标准：后续样本没有出现预设质量退化，且能在不破坏 Issue 恢复状态的条件下回到旧版指导。

### 第四步：有证据后再扩展任务级优化

可以考虑规格修订或 implementation 的工具策略，但试跑必须使用隔离目录，且不能创建真实评论、PR 或合并。
只把已选择产物交回原有工厂流程，并重新完成该代码版本对应的评审、验收和外部操作记录。
通过标准：候选失败不会污染产品分支或业务状态，且端到端收益优于相同预算的简单重试。

## 7. 适用指标

| 目标 | 推荐指标 | 容易造成误导的替代指标 |
| --- | --- | --- |
| 审查质量 | 人工复核的检出率、误报率、证据准确率 | APPROVE 比例、finding 数量 |
| 交付质量 | 当前版本 AC 通过、合并后回归和误完成率 | agent 自称完成、工具退出码 |
| 学习效果 | 留出样本改善、反例覆盖、经验撤回率 | 新增规则数量、反思文本长度 |
| 执行效率 | 达到质量门槛的总成本、总耗时、修订轮次 | 单次模型调用速度 |
| 运行可靠性 | 重启后恢复一致性、无重复外部副作用 | 最终出现过一次成功日志 |

## 8. 决策建议

优先投资“review skill 候选 + harness 快照 + 离线对照 + 保留基线 + 人工 PR 激活”这条最小完整链路。
它与本项目现有能力相接，直接检验持续改进是否有效，也保留了当前交付质量边界。
暂不把多后端扩展、任意插件生成、全阶段递归或全面自改写作为本次启示的实施结论。

如果只能选择一项工作，选择为现有 `improve-review-pr` 增加能够拒绝无效经验的对照验证。
