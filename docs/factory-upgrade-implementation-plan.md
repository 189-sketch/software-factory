## 1. 升级目标与范围

本次升级的目标是建立可恢复、可审计、能够收敛的交付流程。
每次执行都应能回答：依据哪些需求和产物、完成了什么、为什么进入下一步、失败后从哪里继续。

成功标准：

1. 必需工具和规则在 agent 开始执行前已经可用，参数契约只有一个权威定义。
2. 每次阶段执行使用固定版本的输入，修订反馈和已接受决策不因重试、切换角色或进程重启而丢失。
3. 基础设施错误、输出契约错误、质量拒绝和需求冲突分别处理。
4. 审查拒绝必须关联需求、产物版本、规则和证据，建议与措辞优化不得自行变成阻断条件。
5. 已完成的外部操作可以确认和恢复，结果未知的操作不得直接当作失败重复执行。
6. 面板、CLI 与 GitHub 展示能够解释任务当前状态及下一步动作。
7. 已有 issue 可以迁移，不把未知历史伪造成通过记录，不让旧版本和新版本同时写同一任务。

本轮保留现有 TypeScript、Node.js、Harness SDK、CLI、daemon、GitHub 集成和面板。
保持现有配置中的发布、合并和执行权限边界，不因升级默认扩大授权。
新模块数量以职责需要为限，不将本计划中的每个概念都拆成独立服务。

本轮不包含：

- 更换模型供应商、重写 Harness SDK 或增加更多常驻 agent。
- 引入微服务集群、消息中间件或通用 DAG 编排平台。
- 在多台互不共享控制状态的机器之间实现自动抢占和透明故障转移。
- 为所有简单需求立即启用省略规格阶段的快速通道。
- 修改 issue #20 所属业务项目的看板功能。

## 3. 必须先确定的架构契约

### 3.1 执行控制权

每个目标仓库同一时间只有一个具有写入权的控制器。
控制器负责接收命令、保存领域状态、分配阶段执行、计算重试时间、执行或协调外部操作。
worker 负责在分配的工作区内调用 agent、产生候选产物和返回执行结果。
agent 提供内容与判断，不直接决定持久状态转换，也不自行重置执行次数。

本轮允许一个控制器管理多个隔离的 issue worker。
同一 issue 的状态更新必须串行化，其他进程不能绕过控制器写任务状态。
GitHub Actions 与本地 daemon 必须选择仓库级唯一执行模式。
未部署命令接入通道时，两种模式不同时开启。
现有 Actions 单独运行方式在迁移前可以继续使用，但不宣称已经支持与新控制器协同的多主恢复。

### 3.2 状态权威与存储

领域 checkpoint 是流程状态的权威。
不可变产物文件和执行收据是交付证据的权威。
session 是对话与工具调用审计记录，不是自动恢复领域状态的替代品。
GitHub labels、Projects 状态和面板摘要是投影，不作为恢复时覆盖内部状态的隐式指令。

本轮继续使用本地文件存储，明确限定为受支持的本地文件系统和单控制器写入。
每个 issue 的领域状态、事件序号和待执行外部操作放在同一次 checkpoint 提交内。
临时文件替换负责原子可见性，同一 issue 的写入队列负责串行化；不能把 rename 当作跨进程 CAS。
检查点保存增加 schema 版本、单调 revision、校验及恢复检查，并验证 Windows 上的替换行为。
承诺进程退出和重启恢复，存储损坏、磁盘故障或掉电耐久性单独说明，不以进程故障测试代替这些保证。

候选产物先写入独立执行目录，校验后生成不可变版本，再在 checkpoint 中登记引用。
崩溃产生的未登记文件视为孤立产物，不作为已完成结果使用。
自动清理孤立产物不进入首轮升级，先提供可识别记录和人工可审计的清理方式。

### 3.3 领域实体

| 实体 | 最小必需信息 | 核心约束 |
| --- | --- | --- |
| Task | repository、issue、需求版本、生命周期、当前阶段、等待原因 | issue number 不能作为跨仓库全局唯一标识 |
| StageRun | runId、stage、输入引用、执行状态、时间、重试原因、执行版本 | 一次执行一个身份，重试新建记录 |
| ArtifactRevision | artifactId、kind、hash、路径、来源 runId、父版本 | 发布后不可覆盖，审查绑定确切版本 |
| RequirementBaseline | 原始需求、已接受变更、来源及内容版本 | 模型建议不能自动成为用户要求 |
| Decision | 内容、来源类型、依据、作用域、接受状态、替代关系 | 工程假设与用户承诺分别记录 |
| Finding | findingId、规则、严重性、证据、影响需求、产物引用、状态 | 每次修订能追踪解决情况 |
| ExternalOperation | operationId、类型、目标、预期版本、状态、收据、重试时间 | 先保存意图，后执行，结果未知先对账 |

Task 生命周期使用 queued、active、waiting、blocked、completed、failed、cancelled。
StageRun 执行状态使用 queued、running、succeeded、failed、interrupted、cancelled。
APPROVE 与 REJECT 属于审查结果，独立于 StageRun 是否成功执行。
waiting 必须带原因及可用时的 `nextAttemptAt`；blocked 必须说明解除条件。
内容拒绝不直接计为基础设施失败，也不伪装成 agent 执行失败。

### 3.4 输入交接

每次 StageRun 开始前，控制器生成并持久化一个输入清单。
清单包含需求基线、依赖产物版本、待解决 finding、适用决策、必需规则版本、工具清单、允许修改范围和完成标准。
大文件允许通过引用读取，但引用必须可解析且版本固定。
模型第一次能够调用工具之前，必须已收到完整输入清单与强制规则。
上下文压缩可以压缩会话，但不能使输入清单、开放 finding 和完成标准失去访问路径。

不依赖不同 lane 自动继承全部对话。
需要连续的阶段内对话时使用同一 lane；重试可以创建新 lane，但必须恢复输入清单及修正记录。
缓存优化在输入完整性之后进行，不通过先执行任务、再发送依赖的方式实现。

### 3.5 工具与规则

工具的名称、参数 schema、执行函数和必要结果校验由同一注册记录提供。
未知工具或缺失 schema 在启动预检时失败，不退化为空参数对象。
角色必需规则由控制器加载并记录内容 hash，加载失败应在执行前报告配置故障。
skill 工具保留为按需加载补充材料的入口。
审查严重性规则、需求优先级和副作用权限不是可选材料。

### 3.6 失败与恢复分类

| 类型 | 示例 | 处理方与策略 |
| --- | --- | --- |
| transient-infrastructure | 连接中断、服务临时不可用 | 运行时有限重试与退避，写操作先确认结果 |
| resource-wait | 租约占用、worker 不可用 | 调度器记录等待原因与下次调度时间 |
| configuration-or-contract | 必需工具缺失、schema 不匹配 | 报告可操作的阻塞原因，不调用 supervisor 猜测需求 |
| invalid-agent-output | 返回格式不满足契约 | 一次定向修正，仍失败则保留原输出并升级处理 |
| quality-rejection | 规格或实现未满足明确标准 | 生成修订任务，附开放 finding 和版本引用 |
| product-ambiguity | 两个合理解释导致显著不同的用户行为 | product/supervisor 提出具体待决事项，必要时请求用户 |
| external-result-unknown | 推送或合并请求发出后连接断开 | 持久化 unknown，查询远端后再决定继续或重试 |
| interrupted-execution | worker 或控制器退出 | 检查工作区、已登记产物、远端收据后决定续跑或新建执行 |

建议初始策略为：幂等读取的临时错误最多重试 3 次，遵守服务端等待指示并加入退避。
格式错误最多一次定向修正，质量修订最多 3 轮后进入有明确原因的 blocked。
同一未变化的阻塞问题最多一次 supervisor 仲裁，需求或证据变化后才开启新一轮判断。
这些值是待 M0 基线和 M6 试运行校准的初始策略，不是交付效果承诺。
总时长、模型调用量和 token 用量同时设置任务级上限；额度耗尽不能被标记为成功。

### 3.7 审查与收敛

每个阻断 finding 至少包含规则标识、违反的要求、产物位置、可观察影响及建议修正范围。
严重性依据固定规则，而不是关键词或 reviewer 自行扩大的标准。
轻微措辞问题默认非阻断；如果措辞导致行为歧义，必须解释具体影响。
需求变更、工程默认决策和审查建议采用不同来源类型。
自动发布评论记录 operationId、来源角色及内容标记，不根据 GitHub 作者名判断是否为人工指令。
旧评论来源不明时标记 unknown，不自动提升为用户承诺。

每轮 reviewer 先核验既有 finding，再检查修订引入的回归和仍未发现的真实阻断问题。
新 finding 可以阻断，但必须满足同一证据标准，不能以禁止新增意见换取通过。
已拒绝或接受的建议保留处置理由，不能在下一轮无依据重新成为阻断项。
相同产物可以因新增有效证据被重新审查，因此审查记录必须同时绑定产物、需求和规则版本。

### 3.8 外部副作用

内部状态转换与外部操作意图同次持久化，执行器随后处理待执行操作。
不承诺跨本地文件与 GitHub 的全局 exactly-once。
采用可重试执行、稳定身份、查询确认及收据，达到不会无依据重复操作的效果。

| 操作 | 是否阻断后续交付 | 恢复时确认方式 |
| --- | --- | --- |
| 评论、label、Project 展示同步 | 通常不阻断本地修订 | 内容标记或期望展示值 |
| 推送规格或实现分支 | 阻断依赖远端提交的步骤 | 远端 ref 与预期 commit |
| 创建 PR | 阻断要求 PR 身份的审查或合并 | repository、head、base 与记录的 PR 身份 |
| 合并 PR | 阻断任务完成 | PR 合并状态、被审查 head、merge commit 和验证证据 |
| 释放执行租约 | 不抹去已产出的结果，但影响再次调度 | owner、receipt、lease 状态及错误分类 |

内容工作结果和资源收尾结果分别保存。
控制器对未知远端状态进行对账，不重新执行已经确认完成的 agent 阶段。
外部同步不得把较旧 checkpoint 的投影覆盖到较新状态。

### 3.9 租约边界

本轮不通过缩短 TTL 和强制删除远端 ref 来实现自动故障转移。
GitHub ref 的读取、比较和删除不是原子的所有权转移协议，不能宣称它提供严格 fencing。
正常运行由单控制器和执行身份保证本地所有权，远端租约用于防止其他入口竞争。
释放失败保存收据并重试，确认 owner 不匹配时停止删除。
控制器重启后核对未结束 worker 和未释放收据，不能只按时间认定旧执行已经死亡。
所有权无法确认时显示明确 blocked 原因，不忙轮询也不冒险抢占。
如未来必须支持多主自动接管，应另立共享持久协调与 fencing 设计，不在本计划中隐式承诺。

控制器可以调用领域转换、持久化、worker 和外部适配器。
worker 与 agent 不能直接重写任务生命周期。
展示读取器不能通过读取事件自行推断并覆盖领域状态。

## 5. 分阶段实施

### M0：冻结基线，建立真实入口回放

目标：把本次故障转化为稳定、可重复的证据，同时记录当前工作区与安装包的差异。

实施：

1. 记录源码 revision、未提交变更、Node/SDK 版本、目标安装包版本与内容 hash。
2. 复制 issue #20 的 checkpoint、两轮规格、相关会话和日志到独立测试 fixture，移除凭据及不必要的个人信息。
3. 为 fixture 编写来源说明，区分原始证据、重建记录和为了测试构造的后续成功响应。
4. 使用真实 CLI/daemon 入口、真实 Harness 和隔离工作区，外部 GitHub 与模型边界使用可控替身。
5. 先从该入口重现工具契约错误、反馈丢失、提前执行与释放失败后的重复调度。
6. 记录总耗时、模型执行次数、parse miss、修订轮次和已解决 finding，缺失的历史指标明确标注 unavailable。
7. 梳理 `npm test`、`test:fast`、`test:cli` 的覆盖，列出未被默认脚本调用的专项测试。

交付物：基线说明、脱敏 fixture、入口回放工具、测试清单。
验收：同一 fixture 连续运行 3 次得到相同领域结果，测试不访问生产仓库、不发布评论、不修改原始 issue 文件。
依赖：无。
退出条件：失败确实能从用户使用的执行入口被观察，而非仅由静态源码检查推断。

### M1：修复执行可靠性基础

目标：在旧状态格式上先消除已证实的执行缺陷，为架构迁移建立可信运行底座。

实施：

1. 将工具参数 schema 与执行函数统一注册，补齐 `load_skill`，未知注册在预检失败。
2. 为必需规则提供运行前加载，记录角色、规则版本和内容 hash。
3. 将任务和必需上下文装配为第一次执行可见的完整输入，取消逐条上下文触发完整 run 的模式。
4. reroute 按目标阶段保留修订所需产物与反馈，只使受影响的下游结果失效。
5. 保留 supervisor 决策及修正内容，确认 `priorEvents` 或等价的进展摘要真正进入 supervisor 输入。
6. 修复 worker 提前 resolve，分别记录内容结果与租约收尾结果。
7. 为 leased、release-pending 和网络故障增加明确的退避，不因 `ok: true` 持续抢取同一 issue。
8. 核对 fresh lane 的事件过滤、计数、超时和 usage 记录实际生效。
9. 去掉尚未恢复成功的 `self-healed` 语义，先记录恢复计划，后记录恢复结果。

主要文件：`src/core/agent-runtime.ts`、`tools.ts`、`harness.ts`、`llm-agent.ts`、`system-prompt.ts`、`src/orchestrator/index.ts`、daemon 与 lease manager。
验收：F01、F02、F03、F06、F07、F10 的回归测试通过，旧 checkpoint 仍可读取。
验收：第二轮 agent 第一次工具调用前可访问全部修正，租约故障不会掩盖内容结果或触发忙轮询。
发布：可独立作为稳定性修复版本交付，但必须同时验证构建后的安装包。
回滚：本阶段新增字段保持旧 reader 可忽略，不删除旧字段；停止进程并检查在途操作后可回到上一安装包。

### M2：引入领域状态与版本化记录

目标：将任务生命周期、阶段执行、产物版本和外部展示分开。

实施：

1. 确定 schemaVersion 2 和实体最小字段，建立领域转换表与非法转换错误。
2. 每次执行分配 runId，重试、修订和恢复关联前序执行但不覆盖旧记录。
3. 给每次执行绑定 factory 版本、模型标识、规则 hash 和工具契约版本。
4. 保存候选产物的来源、父版本和内容 hash，领域状态只引用已经登记的产物。
5. 同一 issue 的状态变更由控制器串行提交；加入重复结果、旧 revision 结果和旧 worker 回报的拒绝规则。
6. 将 GitHub label 映射保留为入口兼容与展示映射，内部调度逐步改为 stage 和显式命令。
7. 实现只读迁移预览，识别缺失产物、历史冲突与无法确认的执行。
8. 明确控制器锁与仓库执行模式，禁止旧 daemon、Actions 和 V2 控制器同时写入。

主要文件：`src/core/types.ts`、`state.ts`、`src/orchestrator/index.ts`、`runtime/pipeline-definition.mjs`、CLI 和 daemon。
验收：Task active 与 StageRun succeeded/REJECT 可同时正确表达，所有 waiting 均有原因。
验收：重复完成事件不重复推进，旧 run 的结果不能覆盖新输入对应的状态。
验收：迁移预览不改变源文件，缺失审查结果不被补成 APPROVE。
依赖：M0、M1。

### M3：固定阶段输入与统一产物交接

目标：把 session 历史依赖改成显式、可校验的交接契约。

实施：

1. 实现 StageRun 输入清单，持久化需求版本、产物引用、finding、决策、规则和完成标准。
2. SpecAgent 使用候选文件作为正文权威，返回紧凑的产物清单与摘要。
3. 控制器从实际文件读取正文、计算 hash 并校验，不再同时信任工具写入文件和 JSON 内另一份完整正文。
4. PRODUCT 是完成撰写的候选输入时使用准确状态，不在未经审查时称为 already approved。
5. reviewer 读取确定版本的 PRODUCT、TECH 和 diff，并保存审查对象引用。
6. implementation、review-pr、verify-behavior 使用同一种交接方式，保留现有 commit SHA 与验证收据检查。
7. 工作区准备记录基准 commit、允许改动路径和候选产物目录，重试前识别未登记修改。
8. 确认一个 issue 的 worker 不会覆盖其他 issue 的输入、审查临时目录或 session。
9. 中断恢复依据输入清单和已登记产物重建执行，不根据最后一条自由文本推断完成。

主要文件：`src/agents/spec.ts`、`implementation.ts`、`review-spec.ts`、`review-pr.ts`、`verify-behavior.ts`、`src/core/agent-runtime.ts`、`state.ts`。
验收：前后两个 lane 的历史互不继承时仍能正确交接，压缩和重启后依然解析到同一输入版本。
验收：文件与模型摘要不一致时明确失败，旧 hash 或缺失产物不能通过审查或合并。
验收：规格输出契约不再要求返回两份完整文档正文，parse 修复不重复生成整个产物。
依赖：M2。

### M4：审查规则、需求来源与修订收敛

目标：使质量门槛稳定、可解释，并让每轮返工对应明确进展。

实施：

1. 固定审查规则和严重性定义，启动 reviewer 时强制加载并记录版本。
2. 提取 RequirementBaseline，区分用户要求、工程假设、自动评论和已接受的变更。
3. 为 reviewer 输出增加结构化 finding 与证据字段，校验字段完整性和被引用产物是否存在。
4. 将意见维护为 open、resolved、dismissed 或 superseded，并保留处置理由及对应版本。
5. 每轮先评估旧意见，再评估回归和新阻断问题，生成修订范围而非默认整篇重写。
6. 纯格式错误走定向修正，基础设施故障不进入内容仲裁。
7. supervisor 只在争议、无进展或需求歧义时介入，获得完整进展摘要及相关证据。
8. 对需求没有要求的扩展功能、测试工具偏好和非阻断措辞建议设置范围校验。
9. 达到无进展或轮次预算时返回具体阻塞说明，不切换阶段规避预算，也不自动批准。

主要文件：`src/agents/review-spec.ts`、`review-pr.ts`、`triage.ts`、`src/core/types.ts`、相关 skills、orchestrator。
验收：issue #20 的“已完整”不能仅因不常用就成为 CRITICAL，真实跨用户承诺与本地实现矛盾仍被阻断。
验收：自动评论即使与用户同账号发布，也不会自动成为人工决定。
验收：已解决意见必须指向修订证据；新增真实阻断仍可提出并说明理由。
验收：重复相同产物且没有新证据时触发无进展处置，不发生无限返工。
依赖：M3。

### M5：外部操作恢复与明确调度

目标：让进程中断和网络故障不破坏已取得的领域进展。

实施：

1. 引入持久化待执行操作记录，与导致该操作的领域转换一起提交。
2. 先迁移评论和展示同步，再迁移分支推送、PR 创建与合并。
3. 为各操作确定稳定身份、期望远端状态、查询方式和结果收据。
4. 操作状态区分 pending、in-flight、succeeded、retry-wait、unknown、blocked。
5. 启动恢复时对账 in-flight 与 unknown，不能仅按上次退出码决定再次执行。
6. 把 `nextAttemptAt`、等待原因和上次错误写入领域状态，跨进程重启保留退避。
7. 释放失败记录独立于内容成功，持久化 receipt，防止 worker 池重复领取仍待收尾的任务。
8. 检查取消、超时、kill 和控制器重启后的子进程生命周期；失去执行权的 worker 不得发布结果。
9. 合并前重新确认 head、需求/审查版本、验证收据和现有合并配置。
10. CLI 的继续、取消与重新评估通过显式命令生效，旧 label 变更不会静默回退阶段。

主要文件：`src/github/*`、`src/orchestrator/index.ts`、`src/core/state.ts`、daemon、lease manager、CLI、workflow 模板。
验收：外部请求已经成功但响应丢失时，恢复通过查询确认结果，不重复生成内容或产生重复 PR。
验收：展示同步失败不阻断本地规格修订，合并结果未知时不能报告 completed。
验收：租约占用时不在冷却期内重复领取，其他 ready issue 仍能获得 worker。
依赖：M2、M3；最终发布与 M4 的质量证据联调。

### M6：可观测性、迁移演练与逐步发布

目标：交付可运行的新版本，并证明从源码到已安装环境的行为一致。

实施：

1. CLI 与面板读取 V2 领域状态，展示阶段、执行次数、修订版本、阻塞原因、下一次重试和待同步状态。
2. 日志统一包含 repository、issue、runId、stage、artifactId、operationId 和事件类型等适用字段。
3. 在模型 usage 不可用时显示 unavailable，不能记成零成本。
4. 记录恢复计划与恢复结果，删除没有成功证据的自愈统计口径。
5. 更新架构文档、运行手册、配置说明、workflow 边界与安装升级说明。
6. 对旧 checkpoint 执行备份、迁移预览、隔离演练及单项目试运行。
7. 在专用测试仓库验证真实模型、GitHub API、Windows daemon 和安装包路径。
8. 首个项目稳定后再扩大范围，每个仓库保持唯一控制器和明确 schema 写入版本。
9. 发布包写入 build 标识与支持的 schema 范围，启动时拒绝不兼容写入。
10. 稳定性门槛达标后才评估缓存优化和按风险缩短流程，不与可靠性迁移混在同一发布中。

主要文件：`runtime/panel-read-model.mjs`、`panel-api.mjs`、`control-panel`、CLI、构建与安装脚本、docs。
验收：从面板能回答任务为什么等待、依据哪版产物、下一步如何恢复，不需要拼接三个日志文件。
验收：打包安装后的行为测试通过，迁移与回滚演练记录齐全。
依赖：M1 至 M5。

## 6. 建议 PR 拆分与执行顺序

每个 PR 应能说明行为变化、相关证据、验证结果和兼容边界。
阶段拆分用于降低审阅和回滚风险，不代表要同时维护两套可写控制器。

| PR | 内容 | 依赖 | 主要验收 |
| --- | --- | --- | --- |
| 01 | 脱敏基线、入口回放、测试接入清单 | 无 | 真实入口稳定复现问题 |
| 02 | 工具 schema 单一注册、必需规则预检 | 01 | 合法 load_skill 调用成功，缺失工具启动失败 |
| 03 | 首次输入完整、反馈保留、lane 观测 | 01、02 | 第一次执行即可取得依赖与修正 |
| 04 | worker 收尾与租约退避修复 | 01 | 释放故障不被吞掉、不忙轮询 |
| 05 | V2 领域模型、存储、迁移只读预览 | 02 至 04 | 非法转换和旧结果被拒绝 |
| 06 | 固定输入清单、规格候选产物与版本交接 | 05 | 正文唯一来源、hash 校验、跨 lane 交接 |
| 07 | implementation/review/verify 接入版本交接 | 06 | 旧审查与旧验证不能批准新提交 |
| 08 | 需求来源、finding、固定审查规则 | 06 | 阻断有依据，自动评论不提升权限 |
| 09 | 修订进展、预算与 supervisor 边界 | 07、08 | 有限收敛或明确 blocked |
| 10 | 操作记录、展示同步与 PR/merge 对账 | 05、07、08 | 响应丢失不重复操作 |
| 11 | 重启恢复、显式调度、入口排他 | 04、09、10 | 中断恢复和单控制器约束成立 |
| 12 | 面板、CLI、迁移、打包与试运行 | 05 至 11 | 已安装版本端到端验收 |

关键路径：01 → 02/03/04 → 05 → 06 → 07/08 → 09/10 → 11 → 12。
同一分支内的核心状态模型改动先串行合入，避免在共享类型尚未固定时同时重写多个入口。
开发排期以 M0 复现和工作区基线完成后估算为准，本计划不把未知的兼容工作压缩成固定天数承诺。

## 7. 测试与验收矩阵

bug 修复先从 CLI/daemon 的隔离 E2E 入口复现，再编写最小单元回归，随后执行集成和端到端验证。
静态字符串检查只能验证导出、打包或明确的接口边界，不能作为上下文交接、审查收敛或恢复成功的主要证据。
测试替身只放在模型供应商和 GitHub 等外部边界，保留实际 Harness、工具注册、状态存储、调度和工作区路径。
可控模型的后续 APPROVE 是测试输入，不可当作真实模型已经通过质量评估的证据。

| 测试编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| T01 | 所有已注册工具的有效/无效参数 | schema 与实现一致，未知工具不静默运行 |
| T02 | 必需规则加载失败 | agent 未开始执行，错误能定位规则与版本 |
| T03 | TECH 首次执行 | 在首次工具调用前已获得正确 PRODUCT 版本 |
| T04 | REJECT → 修订 → 再审查 | 上轮 finding 与修正完整保留，父产物关系正确 |
| T05 | lane 切换、压缩、进程重启 | 输入引用与未解决问题不丢失 |
| T06 | 同一执行重复返回完成结果 | 不重复推进阶段、不重复外部操作 |
| T07 | 旧 worker 延迟返回结果 | 被识别为旧输入对应结果，不覆盖当前状态 |
| T08 | 用户措辞疑问与真实需求冲突 | 前者不无依据 CRITICAL，后者仍然阻断 |
| T09 | 同账号的自动评论与用户回复 | 来源区分正确，模型意见不自动升格 |
| T10 | 连续同稿、重复意见、新增真实阻断 | 无进展停止有原因，新证据仍能触发审查 |
| T11 | 评论/推送/PR/merge 成功后响应丢失 | unknown → 查询确认 → 正确推进或等待 |
| T12 | 租约释放 EOF、占用、owner 变化 | 收据保留、按计划退避、不删除别人的租约 |
| T13 | checkpoint 写入前后退出 | 读取到有效旧版或新版，恢复动作明确 |
| T14 | 候选文件写入后、登记前退出 | 孤立文件不被当作已批准产物 |
| T15 | CLI/daemon/Actions 同仓库竞争 | 只有一个受支持的写入入口生效 |
| T16 | 两个 issue 同时运行 | 文件、审查目录、session 和收据互不污染 |
| T17 | 新 commit 使用旧 review/verify 结果 | 合并被拒绝并解释失效关系 |
| T18 | V1 状态迁移含缺失 review/correction | 输出不确定项，不伪造批准或用户决策 |
| T19 | 面板等待、阻塞、清理失败显示 | 与领域记录一致，显示原因和下一步 |
| T20 | npm 打包安装到隔离目标目录 | 运行的是新 build，规则、模块与默认测试入口齐全 |
| T21 | 取消、超时与子进程退出 | 不继续发布取消后结果，恢复不遗留未知运行者 |
| T22 | 需求或规则版本变化 | 原审查/验证按影响范围失效，不能沿用旧批准 |

当前可复用的测试入口为 `npm run typecheck`、`npm test`、`npm run test:fast` 和 `npm run test:cli`。
实施时需把本矩阵中的新增用例接入默认 CI，并补齐当前未纳入默认执行的专项测试。
定向测试通过后只执行与阶段改动相关的集成检查；阶段发布前执行完整回归和安装包验证。
发现现存 lint 或测试问题应定位并修复，独立于本次变更的工作单独记录和提交。

真实环境验收要求：

- 在专用测试仓库运行，避免测试评论和 PR 污染生产 issue。
- 覆盖 issue #20 类小功能、真实规格冲突、文案歧义、已有实现修订、外部网络故障五类情形。
- 使用当前实际供应商验证工具调用、结构化输出和 usage；供应商暂时不可用不能算作真实环境通过。
- Windows 是必须验证的平台，使用 PowerShell 原生命令管理文件与后台进程。
- 验证取消和重启时不遗留继续写入的子进程。

## 8. 迁移、发布与回滚

### 8.1 迁移前检查

1. 记录当前源码和已安装包的版本，保留原有未提交改动，不用升级任务顺手覆盖它们。
2. 停止接收新任务，允许已运行任务结束或进入可恢复的中断状态。
3. 确认仓库的本地 daemon 与 GitHub Actions 没有同时运行。
4. 备份 checkpoint、session、操作收据与必要工作区引用，校验备份可读。
5. 对每个 issue 运行只读迁移预览，输出可迁移字段、无法确认内容和建议恢复阶段。
6. 对远端 PR、分支和合并状态进行读取确认，不根据旧 `status` 推断远端结果。

### 8.2 旧状态转换规则

| 旧记录 | 转换规则 |
| --- | --- |
| `merged: true` | 查询确认远端合并事实，无法确认则进入待对账 |
| `status: running` 且无活跃执行 | 转为 interrupted 对应的待恢复任务，不新造运行者 |
| `nextLabel` | 仅作为迁移阶段提示，结合有效产物和远端事实判断 |
| `attempts` / `agentFailures` | 保留为 legacy 计数，不冒充新 StageRun 数量 |
| specs/review 存在 | 校验文件、hash、commit 和对应关系后登记历史产物 |
| specs/review 已删除 | 从可验证证据重建或标为缺失，不自动批准 |
| `self-healed` | 迁移为历史恢复决策事件，不统计为恢复成功 |
| 评论来源不明 | 标记 unknown，不当作用户确认 |

迁移记录来源文件 hash、转换版本和生成时间。
迁移提交前再次检查源文件 revision/hash，源状态已经变化则重新预览。
不在运行中的 V1 checkpoint 上实施原地逐字段修改。

### 8.3 issue #20 的恢复演练

恢复目标是从两轮拒绝后的状态继续，而不是重新开始整个任务。
优先登记可核实的第二版规格、对应 commit、第二轮审查和 supervisor 输出。
如果原始审查只能从不完整日志恢复，保留该限制并重新审查确定版本，不能拼接截断文本假装完整结论。
“已完整”原样登记为用户输入，措辞建议作为待处理意见，不自动视作用户已经同意改名。
先解决租约所有权或外部结果未知问题，再安排下一次修订。
验收结果必须为进入 implementation 或带具体理由的 blocked，不能是无期限 running。

### 8.4 发布批次

| 批次 | 写入范围 | 放行条件 |
| --- | --- | --- |
| A | 隔离回放目录 | M0/M1 回归通过 |
| B | 隔离 V2 状态与测试仓库 | M2 至 M5 的状态与恢复矩阵通过 |
| C | 一个选定目标仓库 | 迁移预览无未解释冲突，完整包安装与恢复演练通过 |
| D | 其余目标仓库逐个迁移 | C 的真实任务和故障恢复证据通过评审 |

读模型可以同时理解 V1/V2，写模型按仓库只能启用一种版本。
新版本启动时检查存储 schema 支持范围，旧版本不得继续写入已经迁移的 V2 数据。
发布时记录模型、规则、工具和 factory build 组合，避免仅以 npm 版本号判断运行一致性。

### 8.5 回滚边界

M1 兼容修复可以在确认在途进程和操作后退回旧包。
V2 尚未写入新进展时，可以停止控制器并恢复迁移前备份。
V2 已产生新产物或远端操作后，不允许直接恢复旧 checkpoint 继续运行旧 writer。
此时优先停止新调度、保存 V2 记录、对账在途操作，然后修复前进。
如必须退回旧版本，需明确导出已确认的新进展、完成远端对账并验证降级转换，不以还原文件掩盖已发生的外部操作。
任何 schema 迁移都必须有对应的隔离回滚演练，不承诺无损自动降级。

## 9. 观测指标与放行标准

| 指标 | 定义 | 初始放行要求 |
| --- | --- | --- |
| 输入完整率 | 首次执行前必需引用与规则均可解析的 run 比例 | 确定性测试 100% |
| 修订可追溯率 | 每次返工绑定前版产物和 finding 的比例 | 确定性测试 100% |
| 恢复正确率 | 故障注入后达到预期状态且无错误副作用的比例 | T11 至 T18、T21 全部通过 |
| 审查依据完整率 | 阻断 finding 的需求、规则和证据字段完整 | 100%，内容正确性另由样本评审 |
| 无进展修订 | 没有有效产物变化或未解释意见变化的轮次 | 达到策略阈值必须停止并解释 |
| 重复外部操作 | 同一逻辑操作生成重复评论、PR 或误推进 | 测试与试运行样本中为 0 |
| 调度空转 | 冷却期内重复领取相同等待任务 | 测试与试运行样本中为 0 |
| 成功交付耗时 | 接收到 verified/merged 的时长 | 与 M0 基线同条件比较，不以删减验收换取下降 |
| 单次交付模型消耗 | 全部阶段、修订、格式修复的实际 usage | 完整记录，缺失显式标记 |
| 人工介入 | 需要人作出产品决策或恢复操作的次数与原因 | 区分合理澄清与系统故障造成的介入 |

对真实模型的收敛率与误报率必须报告样本数、模型与规则版本，不把少量样本外推成总体保证。
严重性误报样本由人工按固定规则复核，不能用另一个模型的单次判断充当最终基准。

## 10. 主要风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 当前工作区存在大量未提交修改 | M0 固定基线并记录文件范围，不覆盖既有工作 |
| 历史被删除，无法完整恢复 | 保留缺失标记，重新核验确定版本，禁止伪造成功 |
| 工具或 SDK 行为与假设不同 | 使用当前锁定依赖做 Harness 行为测试，升级依赖另行论证 |
| 运行与发布包不一致 | 通过隔离安装验证新包，记录 build 与规则 hash |
| 审查校验过严导致无法交付 | 区分结构完整与判断正确，保留争议处置与合理默认决策 |
| 只修格式而不修内容 | Finding 绑定产物证据，修订验证不能只检查 JSON |
| 回滚重复远端操作 | 回滚前对账操作收据，不直接复原过期 checkpoint |
| 单控制器限制与现有多入口习惯冲突 | 仓库级执行模式检查与运行手册明确限制，未来多主单独设计 |
| 状态历史持续增长 | 首轮监测文件大小与读取耗时，确有瓶颈再设计归档或事务存储迁移 |
| 快速通道掩盖质量问题 | 稳定性验收后单独实验，不作为当前升级前提 |

## 11. 完成定义

- M0 至 M6 的交付物、验收记录和兼容边界齐全。
- 已确认的实现缺陷均有通过真实运行路径的回归覆盖。
- 输入、产物、审查和外部操作可以按版本完整追溯。
- 所有合法状态转换、等待原因、预算耗尽和恢复路径均有明确语义。
- 真实模型与 GitHub 测试仓库完成至少一条含拒绝、修订、再审查、实现和验证的完整链路。
- 包安装、Windows 执行、迁移预览、故障恢复和回滚演练全部通过。
- 已有自动合并设置和权限限制继续生效，任何完成结论都对应确切的审查与验证证据。
- 面板与 CLI 能直接解释任务当前状态，文档不再把目标架构描述为已实现行为。
