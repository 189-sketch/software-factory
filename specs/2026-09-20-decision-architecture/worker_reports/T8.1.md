## Deliverable

`runtime/typesafe-backend.mjs` exports one function:

- `runTypesafeStageFromConfig(config, executable, request, opts?) → Promise<StageRunResult>`
  - Mirrors the `runClaudeCodeStageFromConfig` shape (same `(config, executable, request, extra)` signature; `executable` unused for typesafe but kept for symmetry).
  - `opts.env` overrides the credential whitelist (test hook); production callers leave it unset so `agentWorkerEnvironment` is applied automatically — exactly the same hook as `runClaudeCodeStageFromConfig` so the existing T8.0 secret-leak guard (`agentWorkerEnvironment` never forwards `GH_TOKEN` to typesafe) holds.
  - Short-circuit order: `FACTORY_TYPESAFE_OFF=1` → `TYPESAFE_API_KEY` missing → POST to `https://api.typesafe.ai/v1/systemone`. Each branch returns the synthetic fallback envelope documented below.
  - POST body shape: `{ model, state_hash, primitives }` (the `api_key` field is removed from the envelope even when the caller passes it — defence-in-depth so a future refactor cannot accidentally move the credential into the body). `Authorization: Bearer <key>` is the only channel the key travels on.
  - `AbortSignal.any([opts.abortSignal, AbortSignal.timeout(opts.timeoutMs ?? 30_000)])` so a stalled typesafe.ai request never pins the worker.
  - Success path: `{ status: "succeeded", structuredOutput: response.primitives, usage: null, providerSessionId: response.session_id ?? null, warnings: [], retryable: false, backend: "typesafe" }`.
  - Fallback path: `{ status: "failed", output: "", usage: null, logTail: <reason>, backend: "typesafe", warnings: ["typesafe_fallback_to_claude: <reason>"], retryable: false, providerSessionId: null }`. `retryable: false` is contractual — until Phase 11 Slice F (`FACTORY_AGENT_BACKEND_FALLBACK` opt-in) lands, the orchestrator does NOT auto-re-run on Claude.

`runtime/typesafe-backend.d.mts` exports the typed envelope:

- `interface TypesafePrimitive` (`{ id, type: "Choice" | "Score" | "Noul" | "extraction", question, state: JudgmentState }`).
- `interface TypesafeRequest` (`{ model, state_hash, primitives, api_key? }`).
- `interface TypesafeResponse` (`{ primitives: Array<{ id, value, confidence }>, session_id? }`).
- `interface TypesafeAdapterOptions` (`{ fetchImpl?, timeoutMs? }`).
- `interface TypesafeStageOptions` (`{ env?, fetchImpl?, timeoutMs?, abortSignal? }`).
- `function runTypesafeStageFromConfig(config, executable, request, opts?): Promise<StageRunResult>`.

`src/__tests__/typesafe-backend.test.ts` covers:

1. Happy path — 200 JSON response, primitives threaded, `Authorization` header set, body never carries the key, `usage: null`, `providerSessionId` from `response.session_id`.
2. `providerSessionId` falls back to `null` when the response omits `session_id`.
3. `FACTORY_TYPESAFE_OFF=1` short-circuits to fallback; `fetch` never reached.
4. Missing `TYPESAFE_API_KEY` → fallback with `typesafe_fallback_to_claude: TYPESAFE_API_KEY missing`.
5. HTTP 401 → fallback with `typesafe_fallback_to_claude: http 401 ...` (warning surfaces the upstream status).
6. HTTP 503 → fallback with `typesafe_fallback_to_claude: http 503 ...`.
7. `fetch` throws (network / DNS / TLS) → fallback with `typesafe_fallback_to_claude: ECONNREFUSED` (or any thrown reason).
8. Timeout (`AbortSignal.timeout(25ms)` fires) → fallback.
9. Non-JSON response body → fallback with `typesafe_fallback_to_claude: response is not valid JSON: ...`.
10. Non-object JSON response body (e.g. `[1,2,3]`) → fallback with `typesafe_fallback_to_claude: response is not a JSON object`.
11. API key never appears in the body even when the caller accidentally puts it on `TypesafeRequest.api_key`; `Authorization` header carries the real key.
12. Whitespace-only `TYPESAFE_API_KEY` is treated as missing (no `Bearer ` header is sent); `fetch` never reached.
13. `retryable: false` is asserted on four different failure branches (4xx, 5xx, network error, non-JSON).
14. The adapter POSTs to exactly `https://api.typesafe.ai/v1/systemone` (no query string).

## Notes for Reviewers

- `executable` is intentionally unused on the typesafe adapter; the parameter is kept on the signature so every backend-from-config helper has the same shape. A `void executable;` line documents the intent so a future refactor cannot silently drift call sites.
- The fallback envelope is built once in `fallbackResult(reason)`; every branch — `FACTORY_TYPESAFE_OFF`, missing key, HTTP error, timeout, non-JSON — calls the same helper, so the contract bullets in `requirements.md` §"CJK Fallback Contract" cannot drift between trigger conditions.
- The API key is stripped from the body in two places — at `postSystemOne` (where the body is built) and again at the entry point — defence-in-depth so a future refactor cannot accidentally move the credential into the body. The Authorization header is the only channel the key travels on, and no log line ever echoes it.
- `usage: null` is contractual: typesafe.ai does not surface token counts in Phase B; setting `null` rather than `{ inputTokens: null, outputTokens: null }` keeps the synthetic shape distinct from `claude-code` so downstream readers can tell the backends apart.
- `src/core/agent-runtime.ts` is untouched — the dispatcher still returns `backend 'typesafe' is not implemented in this slice` for `runStage`. Wiring the dispatcher to call `runTypesafeStageFromConfig` is out of scope (T9.x).
- `runtime/typesafe-backend.mjs` does NOT log the API key in any branch (success / failure / timeout). Verified by reading the file end-to-end: the only string written to `logTail` is the failure reason (e.g. `http 401`, `ECONNREFUSED`), never the key.
- The `api_key` field on `TypesafeRequest` exists for type completeness; the adapter strips it before serialisation. A future caller-side mistake (e.g. passing `{ ..., api_key: "tk_..." }` in the body) cannot leak the credential because the strip happens regardless.
